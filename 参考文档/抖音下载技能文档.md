# 抖音视频下载

## 适用与前提

- 目标：按视频 ID（19 位数字，如 `7665936241304656379`）下载抖音视频。
- 直接 `curl` 抖音页面/接口会被反爬拦截（返回 JS-glue 页或验证码）；yt-dlp 会报 `Fresh cookies are needed`。**必须走真实浏览器捕获播放流**。
- 无需登录即可下载；登录与否影响可获得的清晰度上限。

## 环境（Windows，托管目录，勿污染全局）

- `agent-browser`（原生二进制，非全局安装）:
  `C:\Users\Administrator\.workbuddy\binaries\node\workspace\node_modules\agent-browser\bin\agent-browser-win32-x64.exe`
  首次需 `agent-browser install`（下载 Chrome）。
- `ffmpeg`（用于合并/校验）:
  `C:\Users\Administrator\.workbuddy\binaries\node\workspace\node_modules\ffmpeg-static\ffmpeg.exe`
  安装：`cd <workspace> && npm install ffmpeg-static --registry=https://registry.npmmirror.com`

## 关键坑（踩过的）

1. **命令输出必须重定向到文件**，管道给 `head` 会触发 SIGTERM（exit 1，看起来像崩溃）。
2. **必须清掉代理环境变量**：`unset HTTP_PROXY HTTPS_PROXY http_proxy https_proxy`，否则浏览器走代理导致 `ERR_TUNNEL_CONNECTION_FAILED` 或页面空白。
3. **Python 里用 subprocess 调 agent-browser 会被 SIGTERM 杀掉**。用 Bash 脚本编排；Python 只做 JSON/HAR 解析。
4. **入口必须用移动端分享页** `https://www.iesdouyin.com/share/video/<id>`，它会自动跳转并正常渲染；直接开 `www.douyin.com/video/<id>` 在本环境渲染为空白页（DOM 只有 3 个节点）。
   > ⚠️ 这条**只适用于 agent-browser（无登录态、无持久 Cookie）这条通道**。
   > 在自建的 QtWebEngine 内置浏览器里**正好相反**：分享页会返回
   > 「验证码中间页」，而 `www.douyin.com/video/<id>` 能正常拉流。
   > 换通道时先把入口顺序调过来试，别照搬。
5. **HAR 不保存响应体**（text 长度为 0），只能拿到请求 URL；想拿接口 JSON 不行。
6. **重放已签名的接口 URL（aweme/detail）会 `Failed to fetch`**（a_bogus 过期），别走这条路。

## 流程

1. 启动 HAR 录制 → 打开分享页 → 等 12s → 执行 `video.muted=true; video.play()` → 再等 18s（等 ABR 升档）→ 停止 HAR。
2. 解析 HAR，收集 `douyinvod.com` 的媒体 URL：
   - `media-video-*` / `media-audio-*`：DASH 分离流（无声/无画面），需用 ffmpeg 合并。
   - 其它路径（如 `.../tos-cn-ve-15c000-ce/xxx/?a=6383&br=...`）：**已合并的 MP4，优先用这个**。
3. **识别归属（关键）**：同一页面会预加载推荐视频的流。URL 带 `&__vid=<目标ID>` 的一定是目标视频；不带 `__vid` 的高码率流多为**同一视频的更高清晰度**（ABR 升档），也可能是推荐视频。判别方法：下载后比对时长，或用 ffmpeg `psnr` 比对画面（PSNR>30dB 即同一内容）。
4. 下载：`curl -sL -o out.mp4 -H "Referer: https://www.douyin.com/" -H "User-Agent: <桌面Chrome UA>" "<url>"`（签名在 URL 内，无需 cookie）。
5. 校验：`ffmpeg -hide_banner -i out.mp4` 看 Duration / 是否有 Video+Audio 两条流。
6. 若为 DASH：下载 video+audio 两条，用
   `ffmpeg -y -i v.mp4 -i a.mp4 -c:v copy -c:a aac -map 0:v:0 -map 1:a:0 -shortest out.mp4`

## ⚠️ 文件名正确 ≠ 内容正确（最重要的教训）

核对本地视频与网页清单时，**只比对标题会得出错误结论**。实测某账号 159 个本地文件：155 个文件名全部能对上网页文案，但内容级抽查 13 个，**仅 3 个真的一致**，其余是「文件名取自目标视频文案、内容却是别的视频」。
成因就是坑 3 的推荐位串流——用户原来的下载工具没做 `__vid` 锁定，批量下载时大面积抓错流。

**任何"是否同步/一致"的结论，必须做内容级校验，不能只比标题。**

### 校验方法（按成本递增）

1. **时长比对（快，约 20s/个）**：打开分享页 → `video.play()` → 读 `video.duration`，与本地 `ffmpeg -i` 的 Duration 比对。
   - 已验证此法可靠：query 得到的时长与真实下载文件的时长完全一致（多个样本差值 0.00s）。
   - 注意 `www.douyin.com` 主站在本环境渲染异常，须走 `www.iesdouyin.com/share/video/<id>`。
   - 判据：差值 ≤1s 为一致；差值有正有负（有的本地长有的短）说明是随机错位，而非剪辑/完整版差异。
2. **画面 PSNR 比对（慢，需先下载）**：
   `ffmpeg -i local.mp4 -i fresh.mp4 -filter_complex "[0:v]trim=0:N,scale=320:180,setsar=1[a];[1:v]trim=0:N,scale=320:180,setsar=1[b];[a][b]psnr=stats_file=-" -f null -`
   - **>30dB（同视频不同清晰度约 45dB）= 同一内容；11~16dB = 完全不同**。
3. 抽样即可定性：抽 10 个若错 ≥3 个，基本可判定为系统性串流问题，需全量体检。

### 常见误判

- **"重复文件"陷阱**：两个文件名相似、标题相近，容易被判为「同一视频的高低清副本」。实测时长 7:59 vs 0:20、22:28 vs 2:42 —— 根本不是同一视频。**判定重复必须先比时长，不能只看名字**。

## 批量修正「名对内容错」的完整方案

当本地文件大面积串流时，按下面流程修复（实测 159 个文件 → 155 个网页视频，最终只需重下 31 个）：

1. **本地指纹**：并发（6 线程）跑 `ffmpeg -i`，提取每个文件的时长/分辨率/大小 → `local_fingerprint.json`。159 个约 3 分钟。
2. **网页时长全量采集**：批量打开分享页读 `video.duration`，写 JSONL 一行一条（**必须断点续传**，155 个约 30 分钟）。
   - ⚠️ **致命坑**：`while read -r VID` 读到的 ID 末尾会带 `\r`（Python 文本模式写文件把 `\n` 转成 `\r\n`）。若直接拼进 JSON，一行会裂成两行，整个文件解析失败、数据全丢（实测一次丢 21 条）。
     必须 `VID="${VID//[$'\r\n']/}"`，且写文件用 `open(..., newline='\n')`。
   - ⚠️ 规整化已有结果时不要用 `open(p,"w")` 原地覆盖（异常会截断文件），用 `tempfile` + `os.replace`。
3. **按时长一对一贪心分配**（容差 0.5s，候选多的先配，同分优先大文件/高码率）→ 得到 locked / rename / download / extra 四类。
4. **歧义消解**：某 vid 若匹配到多个本地文件，用 PSNR 判断这些候选是否同一内容。
   - 候选内容相同（PSNR>30）→ 任选其一，其余作为多余文件。
   - 候选内容不同 → **无法判定归属，必须重新下载**。
   - ⚠️ 若该 vid 同时属于 locked（当前文件名与内容本来就吻合），按「名字即目标」保留当前文件，**不要重下**。
5. **两阶段重命名**（避免目标名互相占用）：先把所有待改名文件改为 `__tmp_NNNN.mp4`，再逐个改为目标名；阶段1后立即持久化 tmp_map 以便失败恢复。冲突的目标名先移入备份目录。
6. **多余文件移入备份目录**，不直接删除。
7. **下载缺失项**：逐个下载并**校验时长**，不符则换下一个候选流；都不符再用 DASH 音视频合并。
8. **最终校验**：逐个检查「文件名正确 + 时长正确」。

### 其它坑

- bash 里 `[ -f "$中文路径" ]` 判断会失效（实测中文文件名返回 false），改用 Python `os.path.exists` 判定。
- 目标文件名生成：desc 中 `#标签` → ` _标签`；去掉 `\ / : * ? " < > |` 与控制字符；长度 >200 时保留「开头 160 + … + 结尾 30」。
- 路径总长要留余量（Windows MAX_PATH 260）。

## 从网页快照(MHTML)提取视频清单

- MHTML 的 html 部分为 quoted-printable，用 Python `quopri.decodestring` 解码。
- 视频卡片：`<a href="https://www.douyin.com/video/<id>">` + 紧随其后的 `<img alt="标题">`（alt 前缀常带「昵称：」需去除）。
- **注意排除页脚「热门」推荐区的 /video/ 链接**，它们不是该账号的作品（曾误判成缺失视频）。判断依据：卡片有封面 img 与特定 class，而页脚链接在 `热门：` 文本附近。
- 本地文件名常被系统 255 字符限制截断（可能掐头），比对时用归一化（只保留中英文数字）+ 包含关系 + 最长公共子串，阈值 0.6。

## 做 GUI 批量下载器时的关键坑（实测记录）

### 媒体流判定：只认 douyinvod
若把 `douyinstatic` 也算作媒体流，会同时踩两个坑：
1. 页面持续加载 JS/CSS → 「最后捕获流后静默 N 秒」的收尾条件永远不成立
   → 每个视频都死等到超时（实测 22s/个，这是**解析慢**的根因）；
2. 会把 `player-*.js` 当视频挑走下载 → 产物只有几百 KB 且**无法播放**。
**只认 `douyinvod` 域名**，显式排除 `douyinstatic` / `douyinpic` / `.js` / `.css`。

### 抓取主页时混入其它主播
- 主页作品接口是 `aweme/v1/web/aweme/post/`；`related` / `recommend` / `feed` /
  `search` / `suggest` / `hot/` 都是推荐位，必须丢弃。
- 过滤其它作者时，**优先从当前 URL 的 `/user/<sec_uid>` 直接取目标作者**，
  不要用「第一个 `aweme/post` 响应里的 `author.sec_uid`」当基准——后者依赖
  响应到达顺序，一旦页面先加载了预取/推荐内容，作者就被锁错，本主播的作品
  会被大面积丢弃（症状酷似「只抓到一两百条」）。
- DOM 兜底只能取主页专属容器（`ul[data-e2e="scroll-list"]` 等），
  绝不能取 `main` / `document`，否则侧栏推荐位会被一并收进来。
- 抓不到时先检查 **sec_user_id 是否正确**：错误 ID 也能打开页面，
  但返回的是整屏推荐位（实测抓到 197 条卖菜刀的，与目标主播完全无关）。
  ID 靠截图肉眼读会错字符——**从 `<profile>` 缓存里正则反查确认**
  （`MS4wLjABAAAA[A-Za-z0-9_\-]{20,60}`，实测真值长度 55）。

### ⚠️⚠️ 采集「中途被截断」的几个真实元凶（实测 630 → 165）
主页明明显示 630，只采到 165。**逐个排查这四处**，都是踩过的：

1. **无条件相信 `has_more`（头号元凶）**：抖音被限流/出小错时也会回一个
   JSON——`status_code != 0`、没有 `aweme_list`，但 `has_more` 常常是 **0**。
   若把任何响应的 `has_more` 都写进状态、再 `if has_more == 0: 结束`，
   采集就会在半途「被骗停」。
   → 只有**真的返回了作品 且 `status_code == 0`** 的响应才有资格改写
   `has_more`/`cursor`；「空页 + has_more=0」要**连续确认 2 次**才算结尾。
2. **「连续无新增」的容忍轮数太短**：`NO_NEW_LIMIT = 12`（每次约 900ms
   ≈ 11 秒）就放弃，而平台翻页太快时会短暂停供十几秒 → 停在半路。
   → 提到 **30 轮（约 30 秒）**，并把 `MAX_SCROLL` 放宽到 500。
3. **滚动到底后 `scrollTop` 不再变化**：`scrollTop` 顶到 `scrollHeight`
   就滚不动，懒加载的 IntersectionObserver 不再触发。
   → 到底时**向上回弹 160px 再到底**，并手动派发一次 `scroll` 事件「顶」出加载。
4. **靠「接口返回条数」判断是否到齐**：接口条数会因限流而暂时停滞。
   → 改成**读页面显示的作品总数**做基准（见下）。
5. **⚠️ 接口钩子偶发完全没命中（实测 630 → 482，最隐蔽的一个）**：
   日志里 `api=0 calls=0` 却 `exp=630`，说明钩子一次都没生效，只能靠
   DOM 兜底。而**抖音主页是虚拟列表**，DOM 里的 `a[href*="/video/"]`
   上限约 **470 个**，硬滚到底也拿不全。
   → 判定条件：`exp > 0 且 calls == 0 且 steps >= 12` 时**重载页面重试**
   （`_reloaded` 标记，**只试一次**，避免死循环）。
   → 排查工具：`tools/probe_api_urls.py`（用拦截器看**所有**请求 URL，
     不依赖页面钩子），能直接看出接口被调了几次、每次返回多少条。

**实测基线（正常时）**：`aweme/v1/web/aweme/post/` 每次只返回 **约 18 条**，
约 **11 条/秒**；630 个作品需要 ~35 次接口调用、约 **55 秒**。
所以 `MAX_SCROLL=500` + `NO_NEW_LIMIT=30` 的耐心是必要的，别再调小。

### 采集数量校准（推荐做法）
- 抖音主页 tab 上有「作品 630」这样的**权威总数**，直接读它：
  先找 `[data-e2e="user-post-count"]`；找不到就**按文档顺序**找第一个
  「作品 + 数字」的小元素（主播自己的 tab 在最上面，先命中即对；
  **不要取最大值**，否则会误收推荐卡片里的数字）。记得支持「万 / 亿」。
- 采集过程显示「**已采集 X / 共 Y**」，到 Y 附近（±3%）自动收工。
- **已知总数且还差得多时，绝不相信 `has_more=0`**——只在「长时间确实没有
  新增」时才放弃。这是防「再次只采一半」的关键。
- 结束时 `X < Y` 要给明确提示，并引导**再点一次采集补齐**（已采到的不重复
  添加）。注意：主页计数可能大于实际列表（实测显示 630、实采 626），
  差的几条通常是已删除/已私密作品，**别当成 bug**。

### 标题为空 ≠ 抓取失败（抖音真的存在无文案作品）
用户看到列表里出现「视频 + 数字ID」时，**先别改代码当成 bug**——
实测某主播 626 条里有 32 条在抖音上**本来就没有文案**：

- 逐字段排查（在空 `desc` 集合内的非空数量）：`item_title`/`preview_title`/
  `caption`/`seo_info.title`/`video_text`/`chapter_abstract`/`share_title` 全为 **0**；
  `chapter_list` 仅 1 条有值；`mix_info` 仅 2 条有值。
- **必须再开视频详情页确认**：详情接口 `desc` 同样为 `''`，抖音自己也没文案。
- 特征：多为某段时间批量上传的短片（实测 28/32 集中在 2019-01~03）。

**正确的修法**（信息不够时别硬编，用真实元数据兜底）：
1. 扩展提取链：`desc → item_title → preview_title → caption →
   seo_info.title → text_extra 话题标签 → chapter_abstract →
   chapter_list[0].desc`（章节标题常是长视频的真实文案）。
2. **合集分集自动编号**：列表接口只给合集名、不给集数，但集数与发布时间同向
   → 按同 `mix_id` 内作品 ID **升序编号**即可。实测算出的「第1集」与
   抖音视频页 `h1` 显示的「第1集 |」一致，可作交叉验证。
3. 兜底命名：有合集 → `合集名 第N集`；否则 → `发布日期 时长`（如
   `2024-04-20 6分42秒`）。目标是**不留一条无名字**。

**数量对不上也别急着找 bug**：抖音主页「作品」计数可能大于实际列表
（实测显示 630、接口与 DOM 卡片都只有 626）。判断漏抓的正确姿势：
`has_more == 0` 且 **DOM 卡片 `ul[data-e2e="scroll-list"] li` 数量 == API 条数**，
就说明抓全了；页面 `a[href*="/video/"]` 去重多出来的通常是侧栏推荐位
（这些节点 `img.alt` 与 `innerText` 均为空，可据此识别）。

### 排查手法（省时间）
- **优先用应用自己的 `ScrapeController` 跑一遍**并落盘 JSON，再离线迭代命名逻辑，
  比反复猜测接口字段快得多。
- 验证命名时**直接调用界面层的真实方法**（如 `DownloadPage.title_of` /
  `build_filename`，用 `type("H",(),{})()` 造个假 self 即可），
  不要复刻一份逻辑——否则验证的是副本，不是真实行为。
- ⚠️ **多个探针不能同时跑**：两个 QWebEngine 进程共用同一个 `WebProfile` 会抢锁，
  日志出现 `Unable to move the cache: 拒绝访问 (0x5)` 后页面会**退化加载**
  （实测只出 21 条就不再加载），极易误判成「抖音限流」。
- ⚠️ 诊断脚本一律用 **`python -u`** 跑：`python x.py > log 2>&1` 时 stdout 是
  块缓冲，进程一旦被信号杀掉或未正常退出，**所有 print 会丢光**，
  只剩 stderr 的 traceback——非常容易误判成"脚本没跑起来"。
- **判断「接口到底调没调」用拦截器，别用页面钩子**：`StreamInterceptor`
  能看到所有请求 URL（含页面自己发的 XHR/fetch）。页面钩子因为注入时机、
  循环导入等原因可能静默失效，用它诊断会得出「抖音没返回数据」的错误结论。
- **先分清「解析失败」和「登录态问题」**：跑一次真实解析器探针
  （`tools/probe_resolve.py N C`）看成功率。如果解析 9/9 成功，
  那用户看到的登录徽标错误就**不是**下载失败的原因，别在登录态上白花时间。

### ⚠️ 批量失败要「可诊断」，别只留一句失败原因
「下到一半整批失败」时，界面上只有一句「未能获取视频地址」，用户完全无从下手。
必须做三件事：
1. **运行日志**（`app/runlog.py`）：写 `<数据目录>/logs/run-YYYY-MM-DD.log`，
   单日 >4MB 重开。任何异常都要吞掉——日志绝不能反过来搞崩主流程。
2. **失败瞬间 dump 页面真实状态**：用 `DIAG_JS` 抓 `location.href`、
   `document.title`、正文片段、`performance` 里 `douyinvod` 资源数、
   是否有 `<video>` 元素。这才能区分「登录墙 / 人机验证 / 页面压根没加载出来」。
3. **连续失败要单独上报**：连续 `STALL_N=3` 条都拿不到流 → 判定为
   **系统性问题**（登录失效 / 人机验证 / 限流），**停止排队**并弹可操作建议
   （重新扫码 / 手动过一次验证 / 并发降到 2~3），而不是让几百条挨个超时。
   拿到流就重置计数（`_consec = 0`），避免偶发单条失败误触发。

### 登录态（QtWebEngine 内置浏览器）
- `cookieStore().loadAllCookies()` 的 `cookieAdded` 信号**在事件循环启动之前就发完了**，
  靠它拿不到已有登录态。**直接读 `<profile>/Cookies` SQLite** ——
  QtWebEngine 存的是**明文**，与 Chrome 的 v10/v20 加密完全不同。
- Chrome / Edge 127+ 的「应用绑定加密」：`Local State` 里
  `app_bound_encrypted_key`（`APPB` 前缀）用用户态 DPAPI 解不开（实测返回 None），
  `v20` 前缀的 Cookie 因此**无法离线解密**；只有老版本的 `v10/v11` 可解。
- ⚠️ 用真实 `--user-data-dir` 启动 Chrome 会**重写并清空其 Cookie 库**
  （实测 123 条 → 0 条）。要读浏览器数据只能读副本，绝不启动它。

#### ⚠️ 「每次打开都要重新登录」的真正原因：Chromium 攒批写 Cookie
Chromium 的 `SQLitePersistentCookieStore` 提交有延迟（约 30 秒一批），
程序被直接关掉时最后一批写入就丢了。判据：
用户 `localStorage.user_info` 里躺着真实昵称（确实登录过），
但 `<profile>/Cookies` 库里 **一条 sessionid 都没有**。
**不要指望调 API 强制 flush——自建一份备份：**
1. 维护内存 Cookie 罐 `{(domain, path, name): {value, expires}}`，
   用 `cookieAdded` / `cookieRemoved` 信号增量更新；
2. 每次变化去抖 ~1.2 秒写入 `session.json`，并在窗口 `closeEvent` 再存一次；
3. **启动时、创建任何 QWebEnginePage 之前**，用 `QNetworkCookie` 把
   `session.json` 里的 Cookie 全部 `setCookie` 注回 CookieStore
   —— 首屏即带登录态，用户无感。
   验证方法：预置一个非 HttpOnly 探针 Cookie，启动后打开抖音读
   `document.cookie`，能看到探针就说明注入在首屏前生效了。

#### QtWebEngine Cookie API 的 6 个事实（都踩过）
1. **PySide6 的 `QWebEngineCookieStore` 没有 `allCookies()`**（只有
   `loadAllCookies()`）→ 必须自己维护 Cookie 罐。
2. **编程式 `setCookie()` 不触发 `cookieAdded`**（只有网络写入才触发）。
   所以「手动粘贴 Cookie 导入」必须**同时**写 CookieStore 和内存罐，
   否则内存罐不知道已登录 → 备份文件里没有 sessionid → 下次仍要重登。
3. `setCookie()` **确实生效**，别被"没有信号"误判为失败
   （用非 HttpOnly 探针 + 页面 `document.cookie` 读回可证）。
4. `deleteAllCookies()` 同样不发信号 → 登出后必须手动清内存罐。
5. **运行时 Cookies 库被独占锁定**：`shutil.copy2` 报
   `PermissionError: [WinError 32]`。读法：先复制，失败则回退
   `sqlite3.connect("file:<path>?mode=ro&immutable=1", uri=True)` 读原库。
6. 信号里 `bytes(cookie.name())` 会报 `string argument without an encoding`
   —— PySide6 这里返回 `str`，写个兼容 str/QByteArray 的转换函数。

#### ⚠️⚠️ 登录态判定：**页面优先，Cookie 只做兜底**（改过一次，别退回）
曾经写成「徽标 = Cookie 判定 AND 页面不是游客态，矛盾时判未登录」，
结果用户**明明已登录**（页面有头像）却一直显示「未登录」。

根因：本环境下 **`cookieAdded` 信号并不可靠**——明文库里躺着 sessionid，
内存罐里却没有。登录是在**不跳转的弹窗**里完成的，`loadFinished` 都未必
再触发，`setCookie()` 又不发信号，于是 Cookie 侧永远补不上。

正确顺序（`ui_browser.py::_refresh_login`）：
1. `dom == "guest"`（页面可见文案是「扫码登录」）→ **未登录**（最可信）
2. `dom == "user"`（页面有可见头像 `img[src*="aweme-avatar"]`）→ **已登录**，
   **不再要求 Cookie 侧也成立**
3. 才回落到 `cookie_ok`

配套修复（`webengine.py`）：
- `_load_cookies_from_disk()` 改成**可反复调用**，用 `(mtime,size)` 做
  `_disk_sig` 缓存；读到的必须 `_remember()` 合并进内存罐（不能只依赖信号）。
- 新增 `_periodic_sync()`：**每 4 秒**轮询明文库 → 登录后几秒内自愈。
- 登录探针 JS 的顺序也很关键：先做廉价 `querySelector`，没有头像才做
  昂贵的「遍历 DOM 逐个量尺寸」，且昂贵那步**限流 10 秒一次**。
- `_restore_session()` 恢复时**跳过已过期的 Cookie**（`exp and exp <= now`
  就 continue），否则注入后立刻被 Chromium 删除，白白触发一轮
  `cookieRemoved`，还会把内存罐搅乱。

#### ⚠️⚠️ 「防复活墓碑」反噬：别让 cookieRemoved 写永久墓碑
为了防「登出后旧 Cookie 复活」，曾给 `_forget()` 加了 `_forgotten` 集合，
并且**任何 `cookieRemoved` 都往里写**。结果出了个极隐蔽的 bug：

会话文件里残留一个**已过期**的 sessionid → 启动注入 → Chromium 判定无效
立刻删除 → 触发 `cookieRemoved` → 记下墓碑 → 明文库里**有效**的 sessionid
之后再也同步不进内存罐 → 界面永远「未登录」。

**修法**：`_forget(domain, path, name, tombstone=False)`，
只有**主动登出**才用 `tombstone=True`；`cookieRemoved` 一律用默认 False。
「明文库是权威」——普通的删除信号不该留下永久墓碑。
防登出后复活已经由 `_logged_out` 标志覆盖，不需要第二层。

验证工具：`tools/verify_login_badge.py` —— 一次跑完三项检查
（明文库有没有 sessionid / 内存罐同步到没有 / 界面徽标文字）。
修好后的健康指标：`logged_in=True`、
`session=['sessionid','sessionid_ss','sid_tt']`、jar 约 62 条（未修时只有 33 条）。

#### 登出要写「墓碑」
登出需做三件事：清 CookieStore + 清内存罐 + 在备份文件里写
`logged_out: true`。墓碑很关键——Chromium 的删除也是攒批写的，
不写墓碑就可能残留；启动时见到墓碑要**跳过明文库种子**并再执行一次
`deleteAllCookies()`，旧 Cookie 才不会复活；再次出现会话 Cookie 时清除墓碑。

#### 测试登录态：把 LOCALAPPDATA 指向临时沙箱
在 import `app.config` **之前**设 `os.environ["LOCALAPPDATA"]=<temp>`，
就能用独立的 profile 跑「保存 → 重启 → 登出 → 再重启」四阶段，
既不污染用户真实配置，也能真实模拟进程重启。

### 下载侧
- 临时文件必须带真实扩展名（`.part.mp4`，不能是 `.part`），否则 ffmpeg 无法推断
  输出容器，报 `Invalid argument` 写不出文件。
- 下完必须校验：`ffmpeg -i` 检查**有视频流 + 时长合理**，并与列表已知时长比对
  （容差 `max(3s, 20%)`）。能挡住「下成 JS 文件」「下到推荐视频」「磁盘满截断」三类坏文件。
- 磁盘写满会让文件静默截断成几百 KB。写入前检查剩余空间，并把
  `OSError(errno=28)` / `No space left on device` 翻译成「磁盘空间不足」。
- Windows DPAPI 的 `CryptUnprotectData` 第三个参数是「可选熵」，必须传 `None`；
  误传输出结构会让解密**恒定失败**（这个 bug 让浏览器 Cookie 导入一直返回 0 条）。

### ⚠️⚠️ 并发：视图必须**复用**，绝不能「用完就销毁再新建」
这是最贵的一次踩坑，症状极具迷惑性：**并发 10 时前 10 条全部成功，
第 11 条起全部失败**（看起来像被平台限流，其实不是）。

- 真因：`QWebEngineView` 用完就 `deleteLater()`、下一条再 `new` 一个，
  **新建的视图之后就再也拿不到视频流了**（Chromium 渲染进程数有上限，
  销毁的进程释放极慢，存活数只增不减）。
- 正确做法：维护**固定大小的视图池**（长度 = 并发数），每个槽位把**同一个
  视图**反复 `load()` 新地址，永不销毁；只在一轮跑完 / 退出程序时
  `stop()` + `load(QUrl("about:blank"))` 放掉页面资源。
- 实测（30 条视频解析）：
  | 方案 | 并发 5 | 并发 10 |
  |---|---|---|
  | 每条新建视图 | 25/25 成功 | **10/25（第 11 条起全灭）** |
  | 视图池复用 | **30/30，0 失败，43.2s** | 23/30 |
  → **默认并发取 5**（用户实测同感），10 路会因 CPU/网络争抢偶发超时。
- 复用视图有个副作用必须防：视图里可能还是**上一条**视频的文档，
  此时 `performance` 读到的直链属于上一条。办法是让探针 JS 同时返回
  `location.href`，**href 里不含目标 vid 就丢弃本次数据**。

### 解析入口：播放页优先，分享页已废
- `https://www.iesdouyin.com/share/video/<id>` 现在返回**「验证码中间页」**
  （普通 HTTP 直接请求也能验证：`<title>验证码中间页</title>`），永远拿不到流。
  旧逻辑「先用分享页、失败再换播放页」等于每条白扔一整个超时。
  → **先用 `https://www.douyin.com/video/<id>`**，分享页只当失败后的备选。
- 播放页本身要 **8~9 秒**才真正拉流（首个 `douyinvod` 出现在 8.7s；
  `document.querySelector('video')` 到 11.7s 才存在；期间 `video.src` 是个
  静态占位 mp4）。并发时会更慢，所以 **`MAX_WAIT` 至少 30 秒**；
  原来给 18 秒会把「慢但完全正常」的视频误判成失败。
- 静默收尾：某条流出现后再等 1.2s 没有新流就收尾，别等满超时。
- 让解析视图「可见」要小心：`WA_DontShowOnScreen + show()`（页面可见）
  **反而更慢**，且只拿到 1 档清晰度；保持**隐藏**（不 `show()`）能拿到 4 档。
- 关图片加载 `AutoLoadImages=False` 对出流时间**没有收益**（8s → 7-8s），
  别浪费时间。

### 断点续传
- 抖音 CDN **支持 HTTP Range**（实测 `Range: bytes=0-2047` → `206`，
  带 `Content-Range: bytes 0-2047/3251342`；注意**必须带完整 UA/Referer**，
  只带 Range 会 403）。
- 实现要点：
  - 每个数据块之间检查 `pause` / `cancel` 两个 `threading.Event`；
    中断抛自定义异常并区分「保留断点」（暂停）与「丢弃临时文件」（停止）。
  - `_fetch()`：文件已有内容就带 `Range: bytes=N-`；**206 追加 / 200 重下 /
    416 视为已下完**。
  - **临时文件名必须稳定且可预测**：目标 `<名>.mp4` → 断点 `<名>.part.mp4`；
    DASH 的中间流也用固定名（`<名>.vpart.mp4` / `.apart.mp4`），
    不要用时间戳——否则续传找不到断点。
  - **不要在下载器内部「自动加序号」**：一旦把 `名字.mp4` 改写成
    `名字 (2).mp4`，续传就找不到原来的 `.part`，断点续传直接失效。
    唯一文件名应由上层在**开始前统一排好**，暂停/继续时沿用同一个名字。
  - 校验失败（坏数据）才删 `.part`；纯网络失败要**保留**，
    这样直链过期后重新解析还能接着下。
  - **⚠️ 只凭「`.part` 存在 + ffmpeg 校验通过」判定「已下完」会翻车**：
    抖音的 MP4 是 **moov 前置**，只下了前面一部分（几十 MB）的 `.part.mp4`
    照样能被 ffmpeg 读出 `Duration` 和视频流，`_verify()` 会**误判通过**，
    于是续传时直接把半成品 `os.replace()` 成成品（实测踩过：32MB 的碎片
    被改名成最终文件，能播但只有前几秒）。
    → 正确做法：下载 + 校验都通过后，额外写一个**完成标记**
    `<名>.part.mp4.done`；只有「标记存在 + 校验通过」才允许改名成成品，
    改完顺手删标记。这样「`.part` 是完整文件但还没改名」和
    「`.part` 只是半截」就能区分开。
  - 判定续传是否真的生效，**看文件大小**最硬：暂停时 `.part` = X，
    续传后成品应等于服务器 `Content-Range` 里的总长（逐字节相等）；
    再用 ffmpeg 确认 `Duration` / 视频流 / 音频流齐全。
- 线程池用**独立**的 `QThreadPool(self)`，不要用 `globalInstance()`，否则会和其他任务抢线程。


### GUI 细节坑（都是「看起来像玄学」的）
- **表格勾选框点不动 / 要点很多次才勾上**：`QTableWidgetItem` 加了
  `Qt.ItemIsUserCheckable` 后，Qt 会在点击勾选框时自己切换一次，而
  `cellClicked` 回调里如果又切一次，**两次抵消 = 点了没反应**。
  → 去掉 `ItemIsUserCheckable`（只设 `CheckStateRole` 数据，
  delegate 依然会画出勾选框），切换逻辑完全由自己的点击处理负责；
  顺便让「整行任意位置」都能勾选，体验好得多。
- **窗口标题重复**（如 `X v1.2.0 - X`）：`setApplicationDisplayName()`
  会被 Qt 拼到 `windowTitle` 后面。删掉该调用即可。
  验证真实标题别用 `windowTitle()`（那只是你设的值），要用 Win32
  `EnumWindows + GetWindowTextW` 读操作系统实际标题。
- **顶部出现一大片「黑色空条」**：不是网页没渲染，而是那条提示 `QLabel`
  被 QVBoxLayout 拉高了——QLabel 默认垂直尺寸策略是 `Preferred`，
  布局有空余时它会**吃掉多余空间**。
  → `setSizePolicy(Preferred, Fixed)` + `setFixedHeight(32)`；
  顺便让这条窄标签当进度条用（「已采集 X / 共 Y」），一举两得。
- **`bitbrowser://` 之类自定义协议会弹系统对话框**
  （「获取打开此 xxx 链接的应用」）：抖音登录弹窗里有这类唤起本机软件的
  链接。要继承 `QWebEnginePage` 重写 `acceptNavigationRequest()`，
  只放行 `http/https/data/blob/about` 等，其它一律 `return False`；
  并设置 `QWebEngineSettings.WebAttribute.UnknownUrlSchemePolicy =
  DisallowUnknownUrlSchemes`。
- **改名要留神**：程序内部「数据目录名 / 注册表键名」和「界面显示名」
  要分开。把数据目录名一起改掉，用户已保存的登录态和设置会全部丢失。
- 失败项建议**自动补一轮**（隔几秒、计数同步回退），用户只点一次
  「开始下载」就尽量跑完，而不是自己去发现哪些失败、再手动点重试。
- **⚠️ 内置浏览器播不了视频（H.264/AAC）是编译期问题**：PySide6 的
  QtWebEngine（实测 140）**不带 proprietary codecs**，`canPlayType('video/mp4; codecs="avc1.42E01E"')`
  返回空 → 页面显示「不支持的音频/视频格式」。无法用命令行开关打开。
  探测工具：`tools/probe_codec.py`（一次 JS 全测完）。
  关键认知：**解析/下载不受影响**——只需要页面发起 douyinvod 网络请求，
  不需要解码播放。处理方式是在界面明确提示「页面视频放不了属正常，
  看视频点『在系统浏览器打开』」，别让用户以为软件坏了。
- **「登录状态」多处显示时必须共用同一份结论**：浏览器页徽标用
  「页面 DOM 优先」判定的同时，侧边栏/状态栏若还用 `pm.logged_in`，
  两处会打架（一已登录一未登录）。让浏览器页发
  `sigLoginState(bool, str)`，其它显示处一律订阅它。
- **检测验证码要在「目标视频 href 校验」之前**：人机验证常是整页跳转，
  href 已不含目标 vid，放在 href 检查后面就永远检测不到。
  检测到后**自动暂停**队列并弹窗引导（去完成验证→回来点继续），
  每轮只弹一次，别轰炸用户。

### 打包
- **`--icon` 只给 EXE 文件本身设图标，不会把 ico 打进运行时包**。
  窗口/任务栏图标要运行时读文件，所以必须再加
  `--add-data app/app.ico;.`，否则任务栏显示默认白框。
- 真正的桌面路径（含 OneDrive 重定向）用
  `SHGetFolderPathW(NULL, 0x10 /*CSIDL_DESKTOPDIRECTORY*/, NULL, 0, buf)`，
  注册表 `User Shell Folders\Desktop` 做备选，`~/Desktop` 只配当最后兜底。

- PyInstaller 的 `--clean` 会批量删除 build 缓存（70+ 文件），**会被安全守卫拦截**
  导致打包失败；`rm -rf build` 同理。
- **重要**：不只是 shell 命令，**Python 里的 `shutil.rmtree()` 同样会被拦截**，
  而且守卫会直接**终止当前进程**。典型症状：日志里只有一行
  `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":103,"threshold":50}`
  然后几秒内 EXIT 1，PyInstaller 根本没启动（前台 print 因缓冲丢失）。
  → 不要以为「改用 Python 删就绕过守卫」，门槛是**删除动作本身**（>50 个文件）。
- **正确做法**：不产生需要清理的旧文件。让 `--workpath` / `--specpath` 指向
  **全新临时目录** `tempfile.gettempdir()/dybuild_<epoch>`，并把环境变量
  `PYINSTALLER_CONFIG_DIR` 也指到临时目录；旧 EXE 用 `os.remove()` 单文件删除
  （1 < 50 阈值，允许）；**项目里的 `build/` 一行代码都别碰**。
- 单次打包 3~5 分钟，产物约 282MB（QtWebEngine 全量 + 82MB ffmpeg）。
- 验证 EXE 是否可启动：`timeout 60 ./app.exe`，返回 **124** 表示进程存活成功；
  控制台出现 `Failed to create GLES3 context / fallback to GLES2` 属无害告警。
- PySide6 排除模块时不能拍脑袋全砍：`QtWebEngineCore` 依赖
  `QtPrintSupport` / `QtWebChannel` / `QtQml` / `QtQuick`，砍了会在运行期报错。
